    Day 1: bring a node into service

    A new GPU node has two questions to answer before a tenant touches it: is it running the right software, and does it actually work? AICR answers the first, NVCRE the second. Both ran on the Paris L4 (21 October 2026) and the Finland 2× H200 node (22 October).

    AICR: a known-good software stack

    The problem

    A GPU server runs a stack of software on top of the hardware: the driver, the GPU Operator that installs and manages it, monitoring, a scheduler. Each piece has many versions, and not every combination works. A wrong one shows up as GPUs the cluster can't see, or crashes after an upgrade.

    Two ways to answer "which versions go together?"

    Part 1: hand-pinned AICR: locked recipes
    How I picked each version and checked it against its release notes NVIDIA publishes tested combinations per hardware, OS and platform
    Output Versions pinned in Git A recipe, rendered as Argo CD apps, plus a validator for a live cluster
    Trust My reading of the notes NVIDIA's testing

    I asked AICR (AI Cluster Runtime, v1.1.0) for both pools and set its answer beside what they run.

    What happened

    • No recipe fits either pool as built. AICR doesn't know the L4 or kubeadm. For the H200 it has recipes, but all of them require Ubuntu 24.04, and the provider's image is 26.04.
    • Its validator refused the H200 node before checking a single component, on the OS release alone.
    • Most versions still match. GPU Operator, NFD and NVSentinel are the same as AICR's. In two places AICR is behind what I need: cert-manager and Kubeflow Trainer.
    • Its drift check missed a change I made by hand, a controller set back one version. Argo CD reverted the same change in 11 seconds.

    What I decided

    AICR is the reference for the H200 pool: the checklist I compare against. It isn't the installer: its bundle would put a second GPU Operator, NFD and Prometheus beside the ones already running. The L4 keeps Part 1's hand-pinned versions, since AICR has nothing for it. Drift detection stays with Argo CD (ADR 0003).

    In one sentence

    I compared Part 1's hand-pinned stack with AICR's locked recipes: AICR is the right reference for a standard H200 pool, but it can't install or validate a cluster that strays from its tested OS, so I use it as a checklist and keep Git as the source of truth.

    Why the drift check missed it

    AICR's snapshot keeps one name: tag per image's last path segment. A digest-pinned image has no tag and reads latest, and both pods were named manager, so they merged into one entry. On a GitOps cluster, Argo CD is the drift detector; aicr diff is useful only for what Git doesn't own (OS, kernel, services), once the counters are filtered out.

    Limits

    • Nothing was installed from a recipe, so AICR building a cluster isn't shown.
    • The snapshot couldn't read the kernel configuration on either site: neither image ships /boot/config-*.
    • One H200 node is one data point for a recipe meant for fleets. Nothing here was simulated.

    NVCRE: certify the node before tenants use it

    The problem. A new GPU server can arrive broken: a faulty GPU, a slow link between GPUs, a bad driver. If customers land on it first, they find the problem for you.

    The idea. Every new server is guilty until proven innocent. It joins the cluster with a "do not enter" sign (a Kubernetes taint, eu1.io/staging), tests run on it, and the sign comes off only if everything passes. That's the gate.

    flowchart LR
  join["H200 node joins<br/>taint eu1.io/staging=pending:NoSchedule"] --> cert["NVCRE certification<br/>nccl-all-reduce<br/>nccl-loopback-nvswitch"]
  join --> diag["ECC mode, then dcgmi diag -r 2<br/>as an NVCRE WorkloadRun"]
  cert --> gate["promote.py<br/>every check passed?"]
  diag --> gate
  gate -->|yes| open["taint removed<br/>tenants can schedule"]
  gate -->|no| keep["taint kept<br/>cause: hardware, tooling or unclear"]

    Making NVCRE work on this hardware

    NVCRE is built for NVIDIA's standard large servers. Mine are smaller and different, so I changed six things:

    NVCRE assumes My reality What I set
    An H200 server has 8 GPUs Mine is a 2-GPU slice of one gpusPerNode: 2 (1 on the L4)
    No speed limit: "passed" only means "it ran" I need proof of NVLink A 64 GB/s floor
    nccl-loopback is the NVLink test That variant switches the GPU-to-GPU path off nccl-loopback-nvswitch, which keeps it on
    Its hardware test is DCGM level 4 About 90 minutes, on a server billed at $11.66 an hour My own level 2 test, a few minutes
    Its controller runs away from GPU nodes The docs say so, nothing enforces it A rule that keeps it off GPU nodes
    Its test pods can enter any node My node carries the "do not enter" sign taintSelectors, so only test pods get in

    NVCRE also relies on two things underneath: Kubeflow Trainer, because it launches each test as a training job (a TrainJob), and the DCGM service the GPU Operator runs on every GPU node, which performs the hardware diagnostic.

    Why a PyTorch image. The speed test needs NCCL (NVIDIA's library for GPUs exchanging data), CUDA, MPI to launch it across GPUs, and NVIDIA's test program all_reduce_perf_mpi. NVIDIA's PyTorch container ships all of them, tested together. It's also what real training jobs use, so the test exercises the same communication stack customers will.

    Driver compatibility. The image (pytorch:26.01) is built for driver 590, and the Finland server runs driver 580. It ran anyway: CUDA 13 programs can run on an older 13.x driver, within limits, and the image also carries its own compatibility libraries. The main test used those; the smaller one used the server's driver directly. I kept pytorch:25.11, built for 580, as a backup. It wasn't needed.

    What I test, and how

    Test Plain English Tool and category
    Can the GPUs exchange data fast? Training splits work across GPUs, which combine their results after every step (all-reduce). A slow exchange means slow training NVCRE, communication/nccl-all-reduce
    Are they on the fast road? NVLink is a private bridge, about 450 GB/s each way. PCIe is the shared main road, about 64 GB/s each way NVCRE, communication/nccl-loopback-nvswitch; pass only above 64 GB/s, which only NVLink reaches
    Is the hardware healthy? Each GPU checks its software, its memory and its PCIe link dcgmi diag -r 2 (DCGM level 2), run as an NVCRE WorkloadRun
    Is memory protection on? ECC catches and fixes memory errors. With it off, the memory test can't run DCGM field 300 (current ECC mode), read just before the diagnostic

    Why the diagnostic runs as a WorkloadRun. A small pod lands on the staged node and asks the node's DCGM service to run the diagnostic. DCGM does the work; the pod is only the messenger, so it needs no special privileges, and it reserves both GPUs so nothing else runs on them meanwhile. I use a WorkloadRun because NVCRE's built-in DCGM test is fixed at level 4, about 90 minutes, and a WorkloadRun is NVCRE's way to run my own test instead. The whole certification stays in NVCRE, with the same entry pass and the same records, rather than me logging into the server.

    NVCRE and the gate. NVCRE runs the tests and reports; it never touches the node. My small script, promote.py, reads every result and removes the sign only if everything passed. When it refuses, it says why:

    • Hardware: the node stays out.
    • Tooling: the test itself broke; a person may override, and the override is recorded.
    • Unclear: a person decides. ECC off falls here.

    What happened on the H200

    • The GPUs exchanged data at 351 GB/s: NVLink proven.
    • The diagnostic passed but skipped its memory test, because ECC was off at the provider.
    • The gate let the node in anyway. That was a gap; it now refuses a skipped test and checks ECC first.
    • 19 min 39 s from server ready to open for customers. Part 1's burn-in took 3 hours and ended with a person running a checklist.

    Why I didn't turn ECC on. ECC only switches on after a GPU reset or a reboot, and on a rented virtual server the GPUs might not come back. It's also the provider's setting: the fix belongs in the handover spec ("deliver with ECC on"), and my gate's job is to catch it, not to patch the node quietly. So the gate refuses the node as "unclear" and I ask the provider.

    In one sentence

    No node takes customer work until it proves its GPUs talk at NVLink speed and pass NVIDIA's diagnostic, enforced by an automatic gate that says why it refuses. I adapted NVCRE to a 2-GPU server, and the H200 run exposed a blind spot that I then closed.

    Setup

    • NVCRE v0.8.0 and Kubeflow Trainer 2.2.1 on the Finland control plane; the six adaptations are in the "In short" tab.
    • The taint goes on at join, through the node's kubeadm JoinConfiguration, so the node is never schedulable before it's checked. NVCRE never taints, cordons or labels a node; promote.py reads its results file, the diagnostic log and the raw NCCL log.
    • Floor: 64 GB/s bus bandwidth. No published figure exists for two H200s in one node. PCIe Gen5 carries 64 GB/s each way and NVLink about 450 (NVIDIA's H200 page), so above 64 the traffic can only have crossed NVLink. It proves the path, not the performance.
    • Test image nvcr.io/nvidia/pytorch:26.01-py3 (built for driver 590), fallback pytorch:25.11-py3 (built for 580), both pinned by digest.

    Paris L4, 21 October

    The same gate with gpusPerNode: 1: certified in 1 min 57 s, diagnostic passed in 11 s (memory included, ECC on), promoted at 17:25:54 UTC. Bus bandwidth is 0 with one rank, so this proved the plumbing, not the L4 (report, gate).

    Limits

    • Level 2 isn't level 4: no targeted power or stress tests, no nvbandwidth, and on the H200 no memory test.
    • One node: no InfiniBand, RoCE, cross-node NVLink or rack-scale NVSwitch, and no training categories (they need 4 or 32 GPUs).
    • Nothing was simulated; only the Paris L4's taint was added by hand, since that node joins without one.

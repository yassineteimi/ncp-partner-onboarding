    HPC: a Slurm group on the same platform, with Slinky

    The problem

    Many research groups have used Slurm, the classic HPC job scheduler, for years. They submit with sbatch and srun and won't rewrite their scripts for Kubernetes. A partner doesn't want a second, separate cluster just for them.

    What I used

    Slinky, SchedMD's own operator, runs Slurm inside Kubernetes: Slurm's scheduler and its worker daemons are pods, on the same nodes, monitoring and health checks as every other tenant (ADR 0007 explains why not Soperator or a separate Slurm cluster).

    Architecture

    flowchart LR
  user["Researcher<br/>sbatch, srun, squeue"] --> login["Login pod"]
  subgraph k8s["Kubernetes cluster, namespace slurm"]
    login --> ctld["slurmctld pod<br/>Slurm's scheduler"]
    ctld --> d0["slurmd pod = Slurm node cpu-0"]
    ctld --> d1["slurmd pod = Slurm node cpu-1"]
    op["Slinky operator"] -->|"creates and keeps<br/>the pods"| ctld
    op --> d0
    op --> d1
    op <-->|"keeps states in sync<br/>(via slurmrestd)"| ctld
  end
  d0 --- node["Kubernetes node<br/>(the Paris CPU worker)"]
  d1 --- node

    Slurm keeps its own scheduler and its own idea of "nodes", but every Slurm node is a pod that Kubernetes places, restarts and monitors. The operator is the translator: it keeps Slurm's view and Kubernetes's view of the same machine in agreement.

    What this shows, beyond "Slurm users can stay"

    Adoption is the obvious part. The less obvious part is one operations model for two schedulers:

    • One maintenance switch. An operator, or NVSentinel, marks a machine unusable once, in Kubernetes, and Slurm stops sending it jobs. Without that link, a partner runs two maintenance procedures and Slurm keeps scheduling onto a node Kubernetes already took out.
    • Health checks flow the other way too. Slurm's own pre-job check drains a sick node, and the operator writes Slurm's drain onto the pod as a condition, where the platform's tools look (seen for the cordon drain; for the pre-job drain my capture read the pod too early to show it).
    • One gate, one fleet (designed for GPU nodes). Slurm would only ever see nodes that passed the Day 1 gate, and a GPU node would move between Slurm and KAI by changing a label and a taint, with no second cluster to rebuild.

    What happened (Paris CPU worker, 21 October)

    Check Result
    A user's jobs srun across both Slurm nodes and an sbatch job completed in 7 s
    A health check before every job A sick node (simulated fault) was drained by Slurm in 1 s; the job was held, then completed once the node was fixed
    Kubernetes and Slurm agree on maintenance Cordoning a worker pod in Kubernetes drained the matching Slurm node in 6 s

    One upstream bug: Slinky's default update mode undid that drain one second later. I switched to the mode that holds it, at the price of a manual step per node on upgrades.

    Slurm with GPUs: designed, not run

    Running it would have meant untested work on a rented H200, so I wrote the design instead:

    • Whole GPUs work with the standard Slurm image; MIG slices and a GPU health check need a custom image (built with NVIDIA's NVML library).
    • Each GPU server belongs either to Slurm or to KAI, never shared: a label and a taint keep them apart, and Slurm's pod takes every GPU on its server.
    • The same certification gate applies: Slurm only sees a server after it passed Day 1.
    • Tenants bring their own container (pyxis), so their CUDA version stays their choice, within the driver's limit.

    In one sentence

    Slurm users keep sbatch, while the partner runs one platform where a single cordon, by a person or by NVSentinel, also drains Slurm, and Slurm's own health checks show up in Kubernetes; the GPU version is designed on paper.

    Setup

    • One Application, slinky: slurm-operator and slurm charts 1.2.3, Slurm 26.05, in namespace slurm on the Paris CPU worker. Two Slurm nodes (cpu-0, cpu-1) on one VM (oversubscribeNode); slurmctld state on a 2 GiB local-path volume.
    • Keys made in the cluster, not in Git: the chart's randAscii + lookup would change on every Argo CD sync (finding), so a wave -1 Job creates the auth and JWT keys once, as immutable Secrets.
    • Prolog 00-node-health.sh: fails if /tmp isn't writable, if under 256 MiB of memory is free, or if the SIMULATED marker /var/run/eu1-simulated-fault exists.
    • No accounting (no slurmdbd), no ssh logins (sssd not wired): the test runs commands in the login pod.

    Slurm with GPUs, Finland: designed, not run

    Written from the source at the pinned versions (slurm-operator and chart 1.2.3, Slurm 26.05.5, GPU Operator v26.7.2, KAI v0.18.6); only helm template was run.

    nodesets:
  h200:
    enabled: true
    replicas: 1                      # one slurmd pod per GPU node
    slurmd:
      resources:
        limits:
          nvidia.com/gpu: 2          # every GPU on the node
    extraConfMap:
      Gres: ["gpu:2"]                # becomes slurmd -Z --conf "Gres=gpu:2"
    updateStrategy:
      type: OnDelete                 # as in Paris, so a pod-cordon drain holds
    podSpec:
      nodeSelector:
        eu1.io/pool: gpu-slurm
      tolerations:
        - key: eu1.io/slurm
          operator: Exists
          effect: NoSchedule
controller:
  extraConfMap:
    GresTypes: [gpu]
configFiles:
  gres.conf: |
    AutoDetect=nvidia
  cgroup.conf: |
    CgroupPlugin=cgroup/v2
    IgnoreSystemd=yes
    ConstrainDevices=yes             # a job sees only the GPUs Slurm gave it
    Topic Design From the source
    GPUs into slurmd Via the device plugin and NVIDIA runtime; ConstrainDevices fences each job The chart enables DCGM for any NodeSet with an nvidia.com/gpu limit
    GRES On the NodeSet, not a NodeName= line Slinky starts slurmd as a dynamic node, slurmd -Z --conf
    Whole GPUs vs MIG AutoDetect=nvidia works for whole GPUs; MIG needs AutoDetect=nvml, so an image rebuilt with NVML The pinned slurmd image has gpu_nvidia.so, no gpu_nvml.so
    GPU health check Prolog dcgmi diag -r 1 via Service nvidia-dcgm:5555 (node-local); needs dcgmi in the image and a UUID map of GPU indices GPU Operator v26.7.2 assets/state-dcgm/0500_service.yaml
    KAI vs Slurm Per node: label eu1.io/pool: gpu-slurm, taint eu1.io/slurm; slurmd takes every GPU; the staging taint applies to both Slinky's workload-isolation guide
    Faults NVSentinel cordons the node, Slinky drains the Slurm node syncCordon holds under any update strategy
    CUDA Tenants bring their container through pyxis; the platform publishes the driver ceiling (CUDA 13.0 native on 580) Slinky's pyxis guide runs the login container privileged

    Not run because every minute is a rented H200, and no check without a GPU reaches what matters: whether AutoDetect finds the GPUs in the pod, whether ConstrainDevices fences them, whether the prolog reaches DCGM.

    Limits

    • Two Slurm nodes on one VM; no shared storage; no accounting or fair share over time.
    • The Paris Slurm is CPU only. Not compared with a bare-metal Slurm.

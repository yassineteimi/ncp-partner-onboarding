    Day 1: no workloads until the node is certified

    The use case

    A new GPU node joins Nordhaven's training pool with a staging taint, so nothing but its own tests can run on it. NVIDIA's Cluster Readiness Engine (NVCRE) certifies it, a DCGM diagnostic checks the hardware, and a small gate removes the taint only if both passed. Part 1 had burn-in scripts and a runbook; this makes the check a gate in front of tenants.

    Ran on the Paris L4 (21 October 2026) and the Finland 2× H200 node (22 October)

    The H200 node was certified at 351 GB/s all-reduce bus bandwidth over NVLink and opened to tenants 19 min 39 s after it was Ready, image pull included. One gap showed up that the gate didn't catch at the time: ECC is off on the provider's H200s, so the DCGM diagnostic skipped its memory test and still passed. The gate now refuses that case. Results.

    The gate

    flowchart LR
  join["H200 node joins<br/>taint eu1.io/staging=pending:NoSchedule"] --> cert["NVCRE certification<br/>nccl-all-reduce<br/>nccl-loopback-nvswitch"]
  join --> diag["ECC mode, then dcgmi diag -r 2<br/>as an NVCRE WorkloadRun"]
  cert --> gate["promote.py<br/>every check passed?"]
  diag --> gate
  gate -->|yes| open["taint removed<br/>tenants can schedule"]
  gate -->|no| keep["taint kept<br/>cause: hardware, tooling or unclear"]

    The taint goes on at join, through the node's kubeadm JoinConfiguration, so there's no moment when the node is schedulable before it's checked. The GPU Operator's operands and NFD tolerate it, since the node is useless until they run. NVCRE injects the same toleration into its own workload pods through taintSelectors, and its run only targets nodes that still carry the taint. NVCRE itself never taints, cordons or labels a node (its README says so), so promotion is mine: promote.py reads NVCRE's results file, the diagnostic log and the raw NCCL log, and says yes only when everything passed.

    When it says no, it also says why, because what happens next depends on it. A hardware failure means no tenant goes on that node. A tooling failure (the run didn't finish, an image couldn't start) allows a manual override, recorded and labelled eu1.io/certification=overridden. Anything in between, for example NCCL leaving NVLink inside one node while the diagnostic is clean, or a diagnostic test that was skipped, goes to a person to decide.

    What NVCRE needed on this hardware

    Read in the source and docs at v0.8.0, and checked by rendering the runs offline with nvcrectl:

    NVCRE default On Nordhaven's nodes Set to
    An H200 node has 8 GPUs The Finland instance, 2H200.141S.88V, is a two-GPU slice of an HGX board; the run finds no node able to supply 8 and fails gpusPerNode: 2
    The L4 isn't in the catalog It falls back to 4 GPUs per node, with a warning gpusPerNode: 1
    No thresholds PASSED only means the test ran A bus bandwidth floor in Finland (below)
    Only DCGM category: level 4 Hardcoded --run 4, about 90 minutes on healthy hardware dcgmi diag -r 2 beside the certification
    Controller "needs a node without GPUs" The docs say so, the chart doesn't enforce it A required node affinity on nvidia.com/gpu.present DoesNotExist
    nccl-loopback Disables P2P and shared memory, so it tests the network path, not NVLink nccl-loopback-nvswitch, the variant that keeps P2P on

    The threshold, and where it comes from

    No published figure gives the all-reduce bus bandwidth of two H200s in one node, and I won't invent one. What I can say from NVIDIA's H200 page is that PCIe Gen5 carries 128 GB/s in total, 64 GB/s each way, and NVLink 900 GB/s, about 450 each way. So the floor is 64 GB/s: above it, the traffic can only have crossed NVLink. It proves the path, not the performance, and I report the measured figure against 450.

    The NCCL log is kept raw, with NCCL_DEBUG=INFO, so the transport each channel used is on record too.

    The image and the driver

    NVCRE runs its NCCL tests in nvcr.io/nvidia/pytorch:26.01-py3, built for driver 590.48.01 (CUDA 13.1.1). The Finland provider's image ships driver 580.178.04. I kept pytorch:25.11-py3, built for 580, as a fallback, after checking its layers for the two binaries the test calls: /usr/local/bin/all_reduce_perf_mpi, and mpirun through /usr/local/mpi, a link to HPC-X. It wasn't needed (below). Both images are pinned by digest.

    The diagnostic's own PCIe test, on the same GPUs, measured 53 to 57 GB/s each way, so the floor sat where it should: just above what PCIe delivers, far below what NVLink did.

    The image question resolved itself, though not the same way for both runs. The MPI all-reduce reported cudaDriverVersion 13010: it ran through the image's CUDA forward compatibility libraries. The single-process loopback reported 13000, the host driver's own CUDA 13.0, and ran through CUDA's minor version compatibility. Either way the 25.11 fallback stayed unused.

The gate now refuses with cause "unclear" when DCGM skips any test, and the diagnostic first records each GPU's current ECC mode, so a GPU with ECC off is refused even before a test gets skipped (ADR 0004).     The L4 test of the same gate

    On 21 October the same gate ran on the Paris L4 with gpusPerNode: 1: staged at 17:23:23 UTC, certified in 1 min 57 s, diagnostic passed in 11 s (software, memory and PCIe, with ECC on), promoted at 17:25:54. The bus bandwidth was 0, as it has to be with one rank, so this proved the plumbing (the taint, the injected toleration, the results file, the log capture, the diagnostic as a WorkloadRun, the gate) and nothing about the L4 (report, gate).

    What level 2 didn't check

    Level 2 isn't NVCRE's level 4: no targeted power or targeted stress (20 minutes each), no nvbandwidth, and on the H200 no memory test either. Level 3 would add the longer stress tests; I haven't run it, and its memory test would only run with ECC on.

    What was simulated

    Nothing on this page. The node, the GPUs, the NVLink traffic and the diagnostic are all real; the only thing staged by hand is the taint on the Paris L4, which joins the cluster without one (what is simulated, for the whole project).

    What one node can't show

    Inter-node fabric: there's one node, so no InfiniBand, RoCE or cross-node NVLink. NVSwitch at rack scale, which NVCRE's multi-node categories exist for. And the training categories, which need at least 4 GPUs (nemotron5-8b) or 32 (nemotron5-56b).

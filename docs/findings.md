# Findings

Things that didn't behave the way the documentation or my first assumption said, and what I changed because of them. One entry each, with a link to the evidence or the file that has the detail. Part 1's findings are on [its own page](https://yassineteimi.github.io/nvidia-gpu-fleet-poc/findings/).

## Verda

- **The image's name gives the CUDA release, not the driver.** "Ubuntu 26.04 + CUDA 13.4 Open" (`26.04.cuda13.4`) ships driver 580.178.04, which is Ubuntu's `nvidia-driver-580-server-open` built by DKMS, with `nvidia-fabricmanager-580` enabled. I had expected the 595 branch that par runs, partly because the confidential-computing variant of the same image says "driver 595" in its name. `/v1/images` has no driver field, so I booted the image on a $0.048/h CPU instance to read it ([inventory](artifacts/fin/image-inventory-20261020T075300Z-rehearsal.txt)). The two sites therefore run two driver branches, which is the trade ADR 0002 is about.
- **Deleting an instance doesn't delete its volumes at the same moment.** I passed both OS volume IDs in `volume_ids` with `delete_permanently: true`. The instances left `/v1/instances` within seconds; their volumes stayed listed as `detached` for another 20 to 40 seconds, then went. My leftover sweep ran inside that gap and reported two billing volumes that were about to disappear, so `make fin-down` now waits for the volumes too ([sweep afterwards](artifacts/fin/rehearsal-20261020-sweep.txt)).
- **An order can fail on Verda's side, and the provider then keeps a ghost in the state.** On 21 October a `CPU.8V.32G` ordered in FIN-01 went to status `error` without ever getting an address, and Verda later listed it as `discontinued`, with its OS volume gone and no charge (the balance read 49.97142 before and after). Terraform provider 1.1.4 reported "Provider returned invalid result object after apply" for every computed field, then kept the instance in the state as tainted. `make fin-down`'s guard refused to plan a destroy for it, as designed, so I removed it from the state by hand after the API confirmed it was gone ([preflight](artifacts/fin/preflight-20261021T121643Z.json), [bring-up](artifacts/fin/cp-bringup-20261021T121643Z.txt)).
- **Terraform provider 1.1.4 leaves the OS volume to the API's default.** Before 1.1.4, `terraform destroy` left every OS volume detached and billing ([issue #17](https://github.com/verda-cloud/terraform-provider-verda/issues/17)). The fix sends `volume_ids: null` and lets the API decide; and the resource's Read errors on an instance that no longer exists instead of dropping it from the state (`internal/provider/resource_instance.go` at v1.1.4). `make fin-down` deletes through the API with the IDs, then removes the instances from the state itself.

## Node bootstrap

- **Part 1 never pinned containerd, and it moved.** Part 1's bootstrap installed whatever `containerd.io` Docker's repository had, which was 2.3.5 and then 2.3.6. Three weeks later the same script got 2.4.2, a release GPU Operator v26.7.x doesn't list: its platform page validates containerd 2.0 to 2.3. I pinned 2.3.6 and rebuilt par's control plane while it was still empty ([node facts](artifacts/par/control-plane-facts.txt)).

## Kubernetes and ArgoCD

- **ArgoCD adds finalizers to child Applications that Git doesn't have.** On v3.5.3, the controller puts pre-delete hook finalizers on the gpu-operator Application and post-delete ones on node-feature-discovery, because their charts carry those hooks. par's root app of apps then showed both children OutOfSync while every child was Synced and Healthy. The root now ignores just those finalizers ([`gitops/sites/par/root.yaml`](https://github.com/yassineteimi/ncp-partner-onboarding/blob/main/gitops/sites/par/root.yaml)).
- **Kubeflow Trainer 2.2.1's chart renders its webhook Secrets empty.** The Trainer and JobSet controllers then write certificates into `kubeflow-trainer-webhook-cert` and `jobset-webhook-server-cert`. ArgoCD saw the filled Secrets as drift, and self-heal put the empty ones back every five minutes, so the controllers kept issuing new certificates. Both Trainer Applications now ignore `/data` on those two Secrets, with `RespectIgnoreDifferences=true`. It's the same family as Part 1's rule about charts that generate secrets.
- **Part 1's Grafana memory limit starved par's etcd through the disk.** At 384Mi, with a 188 MB heap, the kernel kept evicting the Grafana binary's pages and reading them back: 89 GB from disk against 580 MB the process read itself, about 180 MB/s on the control plane's network block disk. I/O pressure there sat at 85%, etcd requests slowed, about twenty controllers lost their leader leases and restarted, and the API server stopped answering for a few minutes. A 1Gi limit brought pressure down to 1% within five minutes. The chart's random admin password also changes `checksum/secret` on every render, so each sync started a new, cold Grafana pod ([evidence](artifacts/par/control-plane-io-20261021.txt)).
- **A powered-off node keeps every DaemonSet one pod short.** I power par's CPU worker off between uses so it stops billing. Left in the cluster as a NotReady node, it held flannel, kube-proxy and node-exporter at one pod of two, and that kept kube-prometheus-stack, and the root Application above it, at Progressing until the worker came back. `make par-cpu-down` now deletes the Node object after the drain. The kubelet still has its credentials on disk and registers the node again on power-on, and `make par-cpu-up` puts its labels back.

## GPU Operator and DCGM

- **dcgm-exporter documents the PCIe byte fields as a rate.** Part 1 declared `DCGM_FI_PROF_PCIE_TX_BYTES` and `DCGM_FI_PROF_PCIE_RX_BYTES` as counters, copied from a commented-out line in `etc/default-counters.csv` at 4.6.0-4.8.3. The same file at [4.8.4](https://github.com/NVIDIA/dcgm-exporter/blob/4.8.4/etc/default-counters.csv), the exporter that GPU Operator v26.7.2 deploys, lists them only as gauges in bytes per second. The shared values now declare them as gauges ([`gitops/values/base/gpu-operator.yaml`](https://github.com/yassineteimi/ncp-partner-onboarding/blob/main/gitops/values/base/gpu-operator.yaml)).

## Scaleway

- **PLAY2-MICRO costs €0.055 an hour, not "about 4 cents".** Part 1's prerequisites page carried the lower figure, and my first budget for this project used it. Scaleway's API read 0.05508 in fr-par-1 and fr-par-2 on 20 October ([prices](artifacts/par/scaleway-prices-20261020.json)). With its 80 GB disk the always-on control plane comes to about €0.065 an hour, or €11 a week.

- **dcgm-exporter starts before the DCGM host engine it needs.** On the L4 on 21 October, GPU Operator v26.7.2's dcgm-exporter 4.8.4 started while `nvidia-dcgm` was still in Init, failed to connect to `nvidia-dcgm:5555` and exited. It went through three restarts in about a minute and then served normally. Nothing was lost, but a restart counter on the exporter means nothing on a fresh node, so alerts on exporter restarts need to ignore a node's first minutes ([acceptance](artifacts/par/acceptance-20261021T165702Z.txt) records the version).

## NVSentinel, NVCRE and AICR

- **NVSentinel's syslog monitor never sees Part 1's simulated XID line.** It reads journald, and journald takes `NVRM:` from a userspace `/dev/kmsg` write as the syslog identifier and strips it from the message. A real driver XID, written by the kernel, isn't affected. Shown on systemd 255 (`fc2-journald-*.txt` in the readiness evidence); an `[uptime]` prefix fixes it, as NVSentinel's own acceptance tests do.
- **Four NVSentinel v1.28.0 defaults would have stopped use case 3.** Drain mode `AllowCompletion` never evicts; the janitor's provider defaults to `kind`, which fakes the reboot; the circuit breaker trips on the first cordon in a cluster with one GPU node and then blocks the uncordon; and the chart in Git uses image tag `main`, so only the OCI chart is pinned.
- **NVCRE v0.8.0 assumes 8 GPUs per H200 node.** It falls back to 4 for a GPU it doesn't know, like the L4, so a 2-GPU H200 node is dropped unless `gpusPerNode` is set. It ships no thresholds, so PASSED means "ran" until you add one. Its only DCGM category is level 4, about 90 minutes. The docs say the controller needs a node without GPUs; the chart doesn't enforce it.
- **NVCRE's NCCL image is built for a newer driver than fin's.** `pytorch:26.01-py3` targets driver 590.48.01, and Verda's image ships 580.178.04, so on the H200 it can only run through CUDA forward compatibility. `pytorch:25.11-py3`, built for 580, is the fallback (`fc11-pytorch-images.txt`).
- **AICR v1.1.0 has no recipe for the stack I run.** `kubeadm` and the L4 are rejected as invalid values; `metal3`, `generic`, `kind` and `bcm` have no H200 Ubuntu training recipe. Every recipe constrains Ubuntu to 24.04, while fin's image is 26.04. Its Kubeflow recipe pins Trainer 2.2.0 in namespace `kubeflow`, where NVCRE v0.8.0 needs 2.2.1 in `kubeflow-system`, and it pins cert-manager 1.20.2, below the 1.21 floor in NVSentinel v1.28.0's README.

## Scheduling and Slurm

- **KAI Scheduler's highest tags, v0.20.0 and v0.20.1, were retracted.** Picking the newest tag would have installed a withdrawn release. The pin is v0.18.6, taken from KAI's own support policy instead.
- **The fake GPU operator and the real GPU Operator can't share a node.** The real one rewrites the GPU labels the fake one sets, so par's simulated GPUs live on two KWOK nodes with no kubelet behind them, labelled `eu1.io/simulated=true` ([what is simulated](simulated.md)).
- **KWOK and fake-gpu-operator ship with no nodeSelector.** Left as released, their controllers can land on par's control plane, which has 4 vCPU for etcd, the API server and the base platform. Both are pinned to the CPU worker here. Their KWOK nodes then raised TargetDown for kubelet targets that can never answer, so Prometheus drops them by node name.
- **The Slurm chart regenerates its keys on every ArgoCD sync.** It makes them with Helm `lookup`, which ArgoCD doesn't run, so each sync would have produced new keys. It's Part 1's ArgoCD lesson again. An in-cluster Job now creates the keys once and leaves them alone.
- **Slinky 1.2.3's "Cordoning Pods" path undoes itself under the default update strategy.** With RollingUpdate, the NodeSet reconcile drains the Slurm node for the annotated pod, then in the same pass removes the annotation from every pod it keeps and undrains it. In the [first slurm-test](artifacts/scheduling/slurm-par-20261021T115447Z.txt) the node never drained within 120 seconds, and the operator's own log, not kept in that capture, showed the uncordon one second after the annotation. Slinky's upstream PR 271 describes the same bug. With `OnDelete` the [rerun](artifacts/scheduling/slurm-par-20261021T121647Z.txt) drained the node within 6 seconds. It holds under `OnDelete`.

## KubeVirt

- **Pinning virt-operator by digest doesn't pin the virt-template components.** KubeVirt v1.9.1 deploys virt-template-apiserver and virt-template-controller by default: their `Template` gate is Beta (`pkg/virt-config/featuregate/active.go`), and Beta gates are on unless disabled (`IsEnabled` in `feature-gates.go`). The operator takes them at their own version, v0.2.3, by tag, from a manifest it embeds. Only `VIRT_TEMPLATE_APISERVER_IMAGE` and `VIRT_TEMPLATE_CONTROLLER_IMAGE` on virt-operator override that (`components/virttemplate.go`, `util/config.go`). I had accepted them as unpinned because I thought the gate was off; the first deployment on par showed them running from tags ([capture](artifacts/platform/kubevirt-20261021T103649Z.txt)). Both are now pinned by digest.

- **`aicr diff` missed a version changed by hand.** On par I set NVCRE's controller from v0.8.0 back to v0.7.0 with ArgoCD paused for that Application. `aicr diff` between the snapshots before and after reported 16 changes, all runtime counters (sysctl values, a random UUID, containerd and kubelet memory), and not the image. AICR's snapshot keeps one `name: tag` per image's last path segment. An image pinned by digest, as everything here is, reads `latest`, and both pods were called `manager`. ArgoCD found and undid the same change 11 seconds after it resumed ([drift demo](artifacts/readiness/aicr/drift-demo-par.txt)).
- **AICR's snapshot can't read par's kernel configuration.** Scaleway's Ubuntu image has no `/boot/config-*`, so kernel options aren't in par's snapshots ([agent log](artifacts/readiness/aicr/snapshot-par-20261021T105254Z.yaml.log)).
- **NVCRE's v0.7.0 controller doesn't start with the v0.8.0 chart's arguments.** It exits on `unknown flag: --namespace-access-timeout`, so the controller image and the chart have to move together. The rolling update kept the v0.8.0 pod serving the whole time ([drift demo](artifacts/readiness/aicr/drift-demo-par.txt)).

## Thanos

- **kube-prometheus-stack 91.4.1 rewrites the Thanos sidecar's bucket config.** It keeps only `existingSecret.name` and `key` (or its own inline secret) from `prometheusSpec.thanos.objectStorageConfig` and silently drops anything else, `optional` included (`templates/prometheus/prometheus.yaml` at 91.4.1). ws-platform's first overlay rendered with no bucket at all, and only the render check caught it. Without `optional`, par's Prometheus can't start until the Secret exists, so the Secret is now written at sync wave -1 instead of with Garage at wave 5.

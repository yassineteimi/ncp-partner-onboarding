    Day 2: from a GPU fault back to service, with NVSentinel

    The use case

    A GPU fails in the middle of a training run. Software should notice, take the node out of service, move the work, repair the node and bring it back, with nobody awake. Part 1 did this with a controller I wrote; here NVIDIA's NVSentinel does it on the same L4, with the same training job and the same injected fault, and I compare the two timelines phase by phase.

    Ran on the Paris L4, 21 October 2026

    Fault to resumed training in 288.8 seconds against Part 1's 360.9, goodput 73.0% against 66.4%, and no person involved at any step. The time didn't disappear, though: 82% of it is now a reboot and a driver rebuild that Part 1 never did. Results, evidence.

    Part 1, the number to beat

    In Part 1 a simulated XID 79 hit a training job at step 394 and cost it 360.9 seconds of outage; the run finished at 66.4% goodput (918.2 s useful out of 1383 s). Most of that outage wasn't the fault at all:

    Phase Seconds What it was
    Lookback 299.4 A five-minute rule I wrote, because node-problem-detector replays old kernel lines when it restarts
    Waiting for a person about 40 Nobody had run make return-to-service yet
    dcgmi diag -r 2 6 The diagnostic that decides whether the GPU can go back
    Reset and uncordon 12 Restarting node-problem-detector so its condition cleared
    Restart 3.9 Scheduling, container start, CUDA start

    83% of it was my timer and 11% was a human. That's what NVSentinel has to answer: does a maintained, event-driven pipeline remove those two, and what does it cost instead? (Part 1, session D)

    What NVSentinel does with an XID 79

    Read in the source at v1.28.0, before trusting anything else:

    flowchart LR
  inj["SIMULATED XID 79<br/>kernel log line"] --> sys["syslog-health-monitor<br/>reads journald every 15 s"]
  sys --> pc["platform-connectors<br/>node condition, MongoDB event"]
  pc --> fq["fault-quarantine<br/>cordon"]
  fq --> nd["node-drainer<br/>evicts through the Eviction API"]
  nd --> fr["fault-remediation<br/>XID 79 = RESTART_BM"]
  fr --> j["janitor<br/>RebootNode"]
  j --> jp["janitor-provider generic<br/>busybox Job: chroot /host reboot"]
  jp --> back["new boot ID, node Ready,<br/>healthy events, uncordon"]
    • The syslog monitor reads the systemd journal, not /dev/kmsg, and matches the NVRM: Xid (PCI:...) pattern in pkg/patterns/xid.go.
    • XID 79 maps to RESTART_BM in NVIDIA's XID catalog, which NVSentinel embeds, so the remediation is a node reboot, not a GPU reset.
    • The node comes back by itself: when the monitors report healthy after the new boot, fault-quarantine uncordons it. Nothing runs a diagnostic first unless post-remediation validation is turned on, and I left it off (see what still isn't automated).

    What I had to change from the defaults

    Each of these would have stopped the run on one GPU node, and each comes from reading the chart at v1.28.0 (nvsentinel-par.yaml):

    Default Why it breaks here Set to
    Drain mode AllowCompletion for every namespace Never evicts: a training job would hold the node until it finished, and remediation would never start Immediate, so the trainer gets the same DisruptionTarget eviction Part 1's Job expects
    Circuit breaker on (50% of GPU nodes in 5 minutes) With one GPU node the first cordon trips it, and a tripped breaker also blocks the uncordon, with no automatic reset Off in Paris. On a fleet I'd keep it, with an absolute cap (maxCordonedNodes) as well as the percentage
    janitor-provider.csp.provider: kind Sleeps a few seconds and reports a reboot that never happened generic: a privileged busybox Job that reboots the node
    MongoDB through Bitnami The Bitnami images are amd64 only, so the values I test on an arm64 laptop wouldn't be the values deployed Percona, one member, on local-path

    Part 1's injection needed a change too. Its kernel log line never reaches NVSentinel: a line written to /dev/kmsg from userspace gets logged at LOG_USER, and journald then treats NVRM: as the syslog identifier and strips it from the message, so the pattern can't match. A real XID comes from the kernel and keeps it. I showed this on systemd 255, the version the Paris nodes run (fc2-journald), and the injection now puts the node's uptime in front of NVRM, which is also how NVSentinel's own tests write it. Same write, same moment in the run, one prefix.

    How I measure it

    The training job, its checkpoints in Garage and the goodput analysis are Part 1's, unchanged, so 66.4% and the new figure mean the same thing. The injection time comes from the L4's own clock, in the same SSH command that writes the line. Everything after it comes from a recorder on my laptop that watches the node, the trainer's pods, the RebootNode objects and the GPU Operator's pods, with the clock offsets between laptop, node and control plane measured at the start.

    Phase Ends when
    Detection NVSentinel's node condition goes True
    Quarantine The node is cordoned
    Drain The trainer pod is gone
    Remediation A RebootNode exists
    Reboot The node is Ready on a new boot ID
    Driver The GPU Operator has rebuilt the driver and the GPU is allocatable again
    Return The node is uncordoned
    Resume The next attempt starts loading its checkpoint

    Why the outage is still almost five minutes

    The waiting is gone: no timer, no person. What replaced it is work Part 1 skipped. Part 1 treated XID 79 by running a diagnostic and handing the GPU back; NVIDIA's catalog says XID 79 ("GPU has fallen off the bus") needs a reboot, so NVSentinel reboots. On the Paris L4 that costs 238 s: 115 s for the VM to come back and 123 s for the GPU Operator to rebuild the driver, because the operator compiles it on the node at every boot there. A precompiled driver would take most of those 123 s away; that's a trade for the driver decision (ADR 0002), not for this page. On a fleet the job wouldn't wait for any of it: it would restart on another node as soon as the drain finished, about 3 s after the fault.

    The same fault through DCGM

    After the measured run I injected XID 79 a second way, into DCGM's cache, with no training running. The DCGM monitor raised GpuAllWatch (DCGM_FR_FALLEN_OFF_BUS) and the node was cordoned 5.7 s after the injection; it was Ready on a new boot 103.8 s later, allocatable 121.4 s after that, and uncordoned 52.4 s after that: 283.3 s in all, within 6 s of the first run (timeline). Both of NVSentinel's detection paths work on the real L4.

    What went well, and what didn't

    The first real test of three things KIND couldn't show, the syslog monitor, the labeler and a real reboot, passed without a retry, and the [uptime] prefix on the injection did what the journald analysis said it would. The cordon came 1.3 s after the fault, so the fallback I had ready (injecting through DCGM if nothing happened within 2 minutes) was never needed.

    Two things nearly got in the way. Scaleway showed no L4 free in either Paris zone a few minutes before the run; one freed up shortly after. And the Paris API server had stalled at 12:07 UTC that day, when Grafana starved etcd's disk, so every NVSentinel, NVCRE and Trainer controller carried 8 to 10 restarts into the run. The restart counts I took before the injection are what show that the run itself caused only two, both on the L4 when it rebooted (before, after).

    What still isn't automated

    The node went back to tenants without a diagnostic. It returned 32 s after the GPU was allocatable, because the monitors said healthy, and nothing ran dcgmi diag first; Part 1's return did. Post-remediation validation (fault-quarantine's validation with lifecycle-manager) would run a DCGM diagnostic for RESTART_BM before the uncordon. I left it off to measure NVSentinel as shipped, and I'd turn it on for tenants: it adds the diagnostic's minutes to every outage, which is cheap next to a tenant landing on a bad GPU.

    Two more gaps, both read in the source and not exercised here. An XID the catalog maps to CONTACT_SUPPORT leaves the node cordoned until a person acts. And NVSentinel only protects the L4 while the Paris CPU worker is on, since its control pods live there: with the worker off, a fault would be logged by the monitors on the L4 and nothing would act on it.

    What was simulated

    The fault. A healthy GPU can't be made to fall off the bus on request, so every XID on this page was written by a script: XID 79 and XID 13 as kernel log lines, prefixed with the node's uptime, and XID 79 again into DCGM's field cache. Everything after the injection was real: the cordon, the eviction, the reboot of the VM, the driver rebuild, the uncordon and the training job resuming from its checkpoint. (What is simulated, for the whole project.)

    What one L4 can't show

    The job can only resume on the node that failed, where a fleet would move it elsewhere and the reboot would cost the job nothing but the reschedule. And a real XID 79 usually kills the process mid-step with a CUDA error, where this trainer gets a clean SIGTERM from the eviction.
